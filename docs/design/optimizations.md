[`../verification/bench.md`](../verification/bench.md)、過程（何を疑い、何を試し、何を捨てたか）は

## 3. 各改善の解説

### 3.1 統計のカウンタが最大の無駄だった（#1）

**症状**: 命令ループの素の速さを測る `loop_while_add` などが本家の 4 倍。

**原因**: 実行ループに `self.op_counts[byte as usize] += 1;` の 1 行があった。Playground の opcode ヒストグラムと、
本家テストの「Opcodes executed: n / 119」のための統計で、`Vec<u64>` への加算。計画では「せいぜい 1%」と見ていたが、
この行を消しただけのビルドと比べると、`loop_while_add` で **25%**、`bm_so_mandelbrot` で **21%** 違った。
1 命令あたり 5〜7 ns の世界では、(1) `Vec` のデータポインタと長さの読み直し（`&mut self` が動き回るので毎回）、
(2) 範囲チェック、(3) 同じ番地（同じ命令が続けば同じ 8 バイト、違っても同じキャッシュライン）への
読んで足して書く、が毎命令つながり、(3) のストア→ロードの依存鎖だけで 1 ns 前後を占める。

**変更**: `[u64; 119]` の固定長配列を `Vm` の中に直に置き、添字を生のバイトではなく解読後の `op as usize` にした
（列挙が 119 variant なので範囲チェックが消える）。そのうえで実行時フラグ `count_ops` を足し、**既定はオフ**。
`Vm::set_op_counting(true)` で数える（Playground と `mrbtest` はオンにする）。

**捨てた案**: 「`Vec` のまま、フラグで数えない」——数えるのをやめたのに、固定長配列で数え続けるより遅かった
（ポインタと長さの読み出しが残り、そこに分岐が足される）。器を変えないと分岐だけでは勝てない。
feature で消す案は、CLI が既定で有効にするとベンチに戻り、無効にすると `mrbtest` の統計が出せなくなるので採らなかった。
フラグ版と「コードが無い」版の差は 2.6〜6.7% しかない。

**本家との関係**: 本家は同種の計数を `MRB_DEBUG` 系のビルド時設定に閉じている。統計はオプトイン、が正しい形。

### 3.2 毎命令のフレーム情報の複製（#2）

**症状**: 命令ループ・呼び出し・データ構造、すべてに薄く乗っていた。

**原因**: ループの先頭で `let ci = self.ci.last().unwrap().clone();` として `CallInfo`（13 フィールド、56 バイト）を
丸ごと複製していた。命令本体が使うのは `base`、`irep`、`pc` の 3 つ。複製そのものに加え、複製を持ち続けることで
レジスタが圧迫される。

**変更**: 3 フィールドだけを Copy で取り出す。5 候補の中で最も広く効いた（`bm_so_mandelbrot` −7.1%、`loop_times` −6.0%、
`ds_array` −5.7%、fib −4.5%）。

### 3.3 メソッド探索が値を複製して返していた（#3）

**症状**: 段階 3 で `Method` に `Arc<dyn Fn>` を持つ variant（クロージャ）を足したら、fib が 4% 遅くなった。

**原因**: `find_method` が `Method` を値で返し、呼び出し側が `#[derive(Clone)]` で複製する。variant がすべて Copy 相当の
間は 16 バイトの memcpy だったが、`Arc` が入ると「判別子で分岐して、片方の腕で atomic 増加」になる。
呼び出しごとにそれが走る。

**変更**: ディスパッチ経路には Copy な `MethodRef`（`Ruby(ObjId)` / `Native(fn)` / `Closure(u32)` など）を返す
`find_method_ref` を用意し、クロージャの実体は必要になったときだけ `closure_of` で引く。
fib −5.2%、`call_args` −4.7%、`app_tak` −6.3%。段階 3 で失った分がそのまま戻り、さらに速い。

### 3.4 `unsafe` を消した代償を取り戻す（#4）

**経緯**: 命令バイトを列挙 `Op` にする `from_u8` は `transmute` だった（VM の crate で唯一の `unsafe`）。
段階 0 で 119 要素の表引きに変えたら **2.5%**（ディスパッチ律速のループで 6〜7%）遅くなった。`transmute` は範囲チェックだけで
**読み出しが無い**（`u8` と `Op` は同じビット列）のに対し、表引きは毎命令 1 バイト読む。「コストは同じ」という見込みが外れた例。

**変更**: 119 本の `match`（`0 => Op::Nop, 1 => Op::Move, …`、生成器 `tools/gen_opcode.py` が出す）。
判別子と値が同じ列挙なので、コンパイラは `match` を範囲チェックだけに畳む。`objdump` で確かめた: 表引きのロードが消えている。
`unsafe` は 0 のまま、`loop_while_add` −12%、全体 −1.7%。

### 3.5 メソッドキャッシュ（#5）

**原因**: 探索はクラスチェーンを歩いて節ごとに `HashMap<Sym, Method>` を引く。インラインキャッシュは無かった。

**設計で怖いのは速度ではなく無効化**。メソッド表を書き換える入口は 40 か所以上ある（`def`、`undef_method`、`remove_method`、
`alias`、`define_method`、`include`、`prepend`、`extend`、`initialize_copy`、`$~` 系を `Undef` で塞ぐところ、…）。
1 つずつ「ここでキャッシュを捨てる」と書いて回ると漏れる。

**変更**: `ClassData` への可変アクセスは `Heap::class_mut` の 1 本しか通らないことを `grep` で確かめ、
**その 1 行で世代番号（`method_serial`）を上げる**。「クラスに可変アクセスした＝答えが変わったかもしれない」という粗い判定で、
定数代入でもキャッシュが飛ぶが、正しさは漏れない。GC が回収したクラスの `ObjId` が別のクラスに再利用される穴は、
`Heap::alloc` でクラスを作るときにも番号を上げて塞いだ。形は 1024 行の直接マップ（1 way）、行は
`(serial, class, mid, Option<(MethodRef, owner)>)`、見つからなかったことも覚える（`method_missing` の繰り返しのため）。
外れのコストは比較 3 回。

**確認**: 20 通りの無効化（定義・再定義・`remove`/`undef`・`include`/`prepend`・特異・`extend`・`define_method`・
`alias`・`private` 化・`class_eval`・`Comparable` の差し替え・…）を、**古い答えを 200 回呼んでキャッシュに載せてから**変更する
スクリプトで確かめ、期待値は本家 4.1.0-rc の出力（`tests/custom/method_cache`）。効果は −1.3% と小さく、
探索そのものより 3.1〜3.3 の方が重かった。

### 3.6 `String#[]` が文字列全体を複製していた（#6）

**症状**: `ds_string`（1500 バイト前後の文字列）の 7 割が `String#[]`。15 バイトなら 98 ms、1500 バイトなら 724 ms と、
**長さに比例**していた。

**原因**: O(n) が 2 つ重なっていた。(1) `bytes(vm, s)` が `to_vec()`、つまり呼ぶたびに文字列全体を複製する。
(2) `char_len` と `char_to_byte` が UTF-8 を 1 バイトずつ歩いて文字を数える。

**変更**: (1) 全体を複製せず、`str_bytes` を短く 3 回借りる形にした（間に挟まる `index_args` は `to_int` を呼ぶことも
例外を投げることもあるので `&mut Vm` が要り、借用を持ち越せない。だから 3 回）。割り当てるのは切り出した断片だけ。
(2) ASCII の早道: `b.is_ascii()`（機械語 1 語ずつ）が真なら文字数＝バイト数。多バイトの文字列は 1 回余分に走る。
1500 バイトの `[]` が 738 → 94 ms（**7.9 倍**）で、15 バイトと同じ速さになった。`utf8` 有りと無しの両方の本家テストが基準どおり。

### 3.7 Hash の走査（#7）と索引（#9、#10）

**症状**: `ds_hash`（1000 要素）で、同じ回数の出し入れが 10 要素なら 94 ns、1000 要素なら 660 ns。差を平均走査長 500 で割ると
**1 要素 1.2 ns**、要素数によらない固定費が **90 ns**（ネイティブ呼び出しと引数の受け渡し）。
`performance.md` の「挿入順の線形探索（本家の AR モードのみ）」の予想どおり。

**#7（定数を落とす）**: 走査のループが 1 要素ごとに `self.heap.get(o)` を取り直していた。鍵の一致確認 `key_eql` は Ruby の `eql?` を
呼ぶことがあるので `&mut self` が要り、借用を持ち越せないため。走査と確認を分け、ハッシュ値の `Vec<i64>` をスライスとして 1 回借りて
`position()` で候補を探し、**候補が見つかったときだけ**借用を抜けて `eql?` を呼ぶ。1 要素 1.2 → 0.78 ns。O(n) は残る。

**#9（入口を 1 本に）**: 索引を足す前に、`HashData` の `entries` と `hashes` を非公開にして 7 つのメソッドを通させた（54 行）。
性能は変えない（−0.3%）。前の担当が数えた書き込み箇所「37 か所」には 1 か所の数え漏れがあり、非公開にしたらコンパイラが指摘した。
3.5 の `class_mut` と同じ考え方で、無効化の抜けをコンパイラに見つけさせる。

**#10（索引）**: 16 要素（本家の AR/HT の切り替えと同じ閾値）を超えたら、`hash 値 -> entries の添字` の索引を持つ。
バケットごとに先頭挿入の 1 本のチェイン、削除で作り直し。挿入順は `entries` の `Vec` が保つ。
キーが `eql?` で一意なので候補の順序を気にする必要がなく、本家より単純に書けた。
`ds_hash` −19.8%、`vm_optimization_bench` −14.4%（中に 5 万要素の Hash 操作がある）。閾値以下しか使わない
`app_json_hash` は ±0。索引ありと索引なし（#9 のバイナリ）で境界（15/16/17/40 要素、閾値を下回る削除、`shift`、
同一 `hash` で非 `eql?` の 25 キー、`rehash`、`replace`/`dup`/`merge`/`clear`/`compact!`）の出力が一致し、本家とも一致
（`tests/custom/hash_index_boundary`）。

**捨てた案**: バケットごとの `Vec<u32>`（キーの数だけ確保する）、削除で索引を捨てるだけ（削除と探索が交互だと二度と作られない）、
tombstone（`entries` の読み手全員が穴を飛ばす必要がある）。

### 3.8 `Array#shift` を O(1) に（#8）

**症状**: 本家のベンチ `bm_so_lists` 3685 ms のうち **2870 ms（78%）**が `shift` 単独。`shift` を `pop` に変えるだけで 446 ms になる。

**原因**: `ObjKind::Array` が `Vec<Slot>` で、`shift` は `Vec::remove(0)`。10000 要素の配列を 10000 回 shift するたびに
約 5000 万要素の前詰め（16 バイト × 5000 万 = 800 MB）、それを 300 回。本家はバッファを共有して先頭ポインタをずらす O(1)。

**変更**: `ArrayData { buf: Vec<Slot>, start: usize }`（非公開フィールド、`Deref<[Slot]>`）。`shift`/`shift(n)`/`unshift`/`insert(0)` が
O(1) で、死んだ先頭が生きている部分より長くなったら（`start > len && start > 16`）前詰めする（償却定数）。
`&buf[start..]` で今までどおりスライスが取れるので、`VecDeque` 案より波及が小さく、`pack`・`Struct`・`Marshal` は無変更で通った。
本家の「共有」の意味までは再現していない（「選べる実装」）。`bm_so_lists` 3699 → 999 ms（−73%）。

**隠れていた O(n) が表に出た**: 最初の計測で `ds_array` が **+155%** になった。原因は `ary_aset` の `let len = items(vm, s).len();`
——配列を丸ごと複製して長さだけ見る。`Heap::array` が `&Vec` を返していた間は LLVM がその割り当てごと消していたが、
`&[Slot]` に変えたら消えなくなり、元からあった O(n) が表に出た。長さだけ要る 8 か所を `ary_len` に替えて解消。
「最適化されていたから遅くなかった」コードは、周りを変えると突然遅くなる。

### 3.10 Hash を 1 回引くたびに全鍵を複製していた（#11、#12）

**症状**: 段階 2c で索引を入れて探索を O(1) にしたのに、`ds_hash` は −20% にとどまり、本家比 7.7x が残った。

**切り分け**（要素数だけを変え、引く鍵は先頭の 10 個に固定）: 探索の距離は要素数によらないはずなのに、1 回あたりの時間が
10 要素 44 ns、100 要素 66 ns、1000 要素 367 ns と 1 要素 0.32 ns で伸びる。**要素数に比例する分が残っていれば、それは探索ではない**。

**原因**: `hash_sync`（鍵の `hash` が古くなっていないかを確かめて必要なら計算し直す）が、「古いか」を聞く**前に**全要素の鍵を `Vec` に複製していた。
借用を早く切るために先に集めておく、というよくある形で、必要な場合（`rehash` の後など）にだけ要るものを毎回作っていた。
`vm_optimization_bench` の中の 5 万要素の Hash は、1 回の引きにつき 5 万要素を複製していたことになる。

**変更**: 順番を入れ替えただけ。全体 −11.7%、`ds_hash` 628 → 233 ms（本家比 7.4x → **2.7x**）、`vmo_objects` −85%、
キーワード引数は Hash で渡るので `call_kwargs` も −15%。あわせて `hash_set` が `key_hash` を 2 回計算し、既存の鍵でも String 鍵を
毎回複製して凍結していたのを、1 回・挿入時だけにした（#12。ベンチでは動かないが `h[k] = v` の micro で効く）。

**教訓**: 「固定費 90 ns はネイティブ呼び出しと引数の受け渡し」と 3.7 節に書いたのは間違いで、呼び出しの実費は 28 ns（`Array#[]` で実測）。
残りは Hash 自身の仕事だった。また、計画にあった「Integer/Symbol/String の鍵を Rust で答える早道」は**すでに入っていた**
（本家の `mrb_hash_ht_hash_func` と同じ形）。切り分けを先にしたから、無い仕事に手を付けずに済んだ。

### 3.11 `include?` がループ内で配列を複製していた（#13）

`Array#include?`/`member?`/`count` が 1 要素を比べるたびに `items()`（配列全体の複製）を呼んでいて O(n²)。100 要素の `count` で −86%。
ベンチ 22 本はどれも呼ばないので合計は動かないが、実コードでは普通に使う。`items()` の複製は、3.8 の 8 か所を直した時点で
ベンチからは消えていた（切り分けで確認）。

### 3.9 効かなかった・やらなかったもの

* `Slot` を 8 バイトにする（NaN boxing 相当。`performance.md`）——出発点の計測で「値の出し入れ」は主因でないと分かったので、後回し。
* 鍵が Integer/Symbol/String のときの `hash`/`eql?` の早道——調べたらすでにあった（3.10）。
* `unsafe` による境界チェックの省略、goto threading の模倣——方針としてやらない。
* ネイティブが配列を `items()` で複製する箇所（中身を読むもの）——長さだけの 8 か所は直したが、残りは残っている（5 節）。

## 4. 計測の方法

この一日で分かったことの中で、本に書く価値が一番あるのはこれかもしれない。

* **機械**: i7-13700（P コア + E コア）の WSL2。`taskset` 無しだと E コアに落ちて 20% 遅い。`tools/bench.sh --core 2`（P コア固定）が前提。
* **逐次の best of 5 が当てにならない**。Linux VM の中は idle でも、Windows ホスト側の都合で実行時間が数分単位で 10〜40% 動く。
  「A を 5 回 → B を 5 回」だと 5 回とも同じ遅い窓に入り、best が外乱を弾かない。同じ変更が同じ日の 2 回の計測で **+28% と −12%** に出た。
* **交互 A/B が効く**。1 ラウンドごとに A と B を 1 回ずつ回すと、両方が同じ分の同じ機械に当たるので、ミリ秒は動いても比は動かない。
  `tools/bench_ab.sh`。段階ごとの交互 A/B の積（−20.4%）と通しの計測（−22.0%）が一致した。
* **自分の道具も外乱になる**。計測中に `grep -rn` や `cargo build` を回すと best と median が 17〜44% 離れる。best と median の差が
  0.5% 程度なら静か、1% を超えたら取り直す。荒れている日は min of 15。
* **並行作業のベンチは互いを汚す**。2 人の担当が同じ機械でベンチを回した日の数値は捨てた。ベンチを伴う作業は同時に 1 つ。
* **呼び出しを含まないベンチは候補ごとに ±4〜12% 動く**。9000 行の `exec_frames` のループ本体がキャッシュラインのどこに乗るかの揺れ
  （コード配置）で、1 命令 5〜7 ns で他に何もしていないぶん一番敏感に出る。分類の合計で見る。
* **切り分けは操作ごとの小さなスクリプト**で（`perf` はこの環境に無い）。空ループを一緒に測ってループ分を引く。
  要素数を変えて測ると固定費と 1 要素あたりのコストが分かれる（3.7）。

## 5. 残っている重さ

| 何 | 本家比 | 中身 |
|---|---|---|
| Hash | 2.7x（2d の後） | 残りは Hash 固有の 16 ns（`hash_sync`、`key_hash`、候補探し、`key_eql`）とネイティブ呼び出しの 28 ns。`hash`/`eql?` を Ruby で定義した鍵は 286 ns で、これは本家も同じ |
| `vm_optimization_bench` | — | 2d で `vmo_dispatch`/`arith`/`calls`/`index`/`objects` の 5 本に分けた。元は「実アプリ寄り」に残る |
| `String` | 4.5x | `<<` と `+` の割り当て、多バイト文字列の文字数え |
| `items()` の複製 | — | 残っているが、ベンチではもう効いていない（2d で確認）。呼び出しの多いものから順に |
| 値の表現 | — | `Slot` 16 バイト。8 バイト化は `Slot` の型を差し替えるだけで試せる作りにしてある |
| ベンチの穴 | — | `bm_ao_render` と `bm_mandel_term` は `printf`/`putc` が無くて動かない（出発点から）。`mem_retained` は本家の世代別 GC の弱点を測っているので、本家比 0.5x は SabiRuby が速いのではなく本家が遅い |

## 6. 性能に関わる設計の約束

* **`unsafe` を増やさない**（今 0）。境界チェックの省略や `transmute` で稼がない。
* **統計はオプトイン**（`set_op_counting`、`set_trace`）。既定の実行ループには計数を置かない。
* **書き換えの入口を 1 本にしてから、キャッシュや索引を足す**（クラスの表は `class_mut`、Hash は `HashData` のメソッド）。
  無効化の抜けは人が探すのではなく、コンパイラに見つけさせる。
* **本家の「振る舞い」を再現し、「表現」は選び直す**（配列の共有バッファ、Hash の AR/HT、インラインキャッシュの形）。
  選び直した表現の計算量が本家と違えば、それがそのまま倍率になる（3.8）。
* **変更は 1 つずつ、交互 A/B で測ってから採る**。効かないものは取り込まず、数値だけ残す。
