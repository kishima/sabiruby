# 対応メソッド一覧を生成する（from-mrubyedge-plan 項目 3）

2026-09-16。`docs/plans/from-mrubyedge-plan.md` の項目 3。`tools/mrbtest.sh` が答えるのは
「同じように振る舞うか」で、「そもそも何があるか」は誰も答えていなかった。mruby/edge が
持っている対応メソッド一覧に当たるものを、生成物として `docs/verification/coverage.md` に置く。

## どう取るか

VM の中の話なので、Ruby のスクリプトを両方の VM で走らせて、同じ形の一覧を吐かせるのが一番素直だった。
`sabiruby run tools/coverage.rb` と、Docker の `kishima/mruby:4.1.0-rc`（`tools/custom.sh` が
参照出力を取るのに使っているのと同じ image。`mrbc` だけでなく `mruby` も入っている）の
`mruby /w/coverage.rb`。スクリプトは 1 本で、どちらで走っているかを知らない。

一覧の取り方は 2 つ考えた。`ObjectSpace.each_object(Module)` で生きているモジュールを全部拾う方法と、
`Object` から定数を辿る方法。前者だけだと名前が付かないもの（特異クラス）が大量に混ざる
（SabiRuby で 72、本家で 240）。後者だけだと定数から辿れないものを落とす。両方やって、
定数の木を主にし、`ObjectSpace` で拾えなかった名前付きモジュールを後から足す形にした。
結果としてはどちらの VM でも「定数から辿れない名前付きモジュール」は 0 件だったので、
`ObjectSpace` は今のところ保険でしかない。それでも件数は文書に出している（本家の
特異クラス 240 に対して SabiRuby は 72、という数字自体が何かを示唆しているかもしれない）。

`Module#constants` は両方の VM で自分自身の定数しか答えない（`Integer.constants` が `[]`）ので、
木の探索はそのまま書けた。`Integer.constants` が `Object` の定数まで返すなら重複除去が要る、と
身構えていたが不要だった。

## 最初の版が間違っていた 2 点

**1 つ目。スクリプト自身の `def` が `Object` を汚した。** 最初の出力では
`Object#cov_name` `Object#cov_skip?` `Object#cov_methods` `Object#cov_visit` の 4 つが
「SabiRuby にあって本家に無いメソッド」として並んだ。同じスクリプトを走らせているのだから
両方に出るはずで、おかしい。本家の `Object.instance_methods(false)` は `[]` を返していた。
理由は、mruby ではトップレベルの `def` が `Object` の **private** メソッドを作り、
`instance_methods` は public と protected しか答えないから。SabiRuby はこれを public
にしている。つまりバグ取りのつもりで見た 4 行が、そのまま SabiRuby と本家の食い違いの
報告になっていた（`tests/custom/` に起こすほどの害は無い。`private` を明示した
`private :a` は SabiRuby でも効いていて、`A.instance_methods(false)` は両方で `[]`）。
対処は、最初の `def` より前に `Object` の自前メソッドを控えておき、両方の VM で
その集合に絞ること。

**2 つ目。private を数えないと差分の半分が見かけ倒しになる。** 1 つ目で分かったとおり
`instance_methods` は private を隠す。mruby はモジュール関数を「public な特異メソッド
＋同名の private なインスタンスメソッド」として定義するので、本家側では `Kernel.eval` だけが
見え、SabiRuby 側では public な `Kernel#eval` だけが見える。`Module#private` `#public`
`#protected` `#module_function` `#remove_const` `#included` `#method_added` なども本家では
private で、SabiRuby では public。この状態で差分を取ると、「SabiRuby にしかない 140 個」の
うち数十個が実際には本家にもあるメソッドだった。

`private_instance_methods(false)` が両方の VM にあることを確かめて（SabiRuby の
`Module.private_instance_methods(false)` は `[]`、本家は `[:const_added, :extended, …]` の 12 件）、
public と private の両方を数え、行に可視性を付けるようにした。差分は次のように変わった。

| | 変更前 | 変更後 |
|---|---:|---:|
| 本家にあって SabiRuby に無い（POSIX 除く、答えない） | 10 | 22 |
| SabiRuby にあって本家に無い | 140 | 118 |
| 同じメソッドで可視性が違う | （見えていない） | 45 |

増えた 22 のほうは、`Kernel#gets` のように「本家では特異メソッドと private インスタンス
メソッドの両方がある」ものが両側で数えられるようになったため。減った 118 のほうが
実質で、`Kernel#eval` や `Module#private` のような偽の差分が消えた。

## 差分を 4 つに分ける

素朴に `Class#method` の集合差を取ると、読めない一覧になる。実際に出たのは次の 3 種類の
ノイズだった。

* **POSIX の gem。** image の `mruby` は `default.gembox` に加えて mruby-io / mruby-dir /
  mruby-errno / mruby-socket / mruby-process / mruby-signal が入っている。`Errno::E*` だけで
  136 クラス。SabiRuby は no_std なのでこれらは初めから移植対象外（`docs/design/gems.md`
  「Remaining gems」）。クラス名から gem を引ければ機械的に落とせる。
* **持ち主が違うだけ。** `Integer#<` は本家では `Integer` にあり、SabiRuby では `Numeric` にある。
  `Float#nan?` も同じ（本家は `Float`、SabiRuby は `Numeric`）。呼べば同じように答えるので、
  「無い」ではない。
* **モジュール関数の片割れ。** 上に書いたもの。

そこで、片側にしか無いメソッドを、POSIX / 片割れ / 持ち主違い / 本当に無い、の 4 つに分けた。
「持ち主違い」の判定は `lives()` という awk の関数で、インスタンスメソッドなら相手側の
`ancestors` を順に見る。クラスメソッドは少し厄介で、`ancestors` のうちクラスであるものが
そのまま superclass の鎖になるのでそれを見た後、`Class`（相手がモジュールなら `Module`）の
`ancestors` も見る。後者が要るのは `Module#name` のようなものがクラスメソッドとして呼べるから。

この 2 段目を書いていて、`Kernel.eval` が SabiRuby で通る理由に気づいた。SabiRuby は
`Kernel#eval` を public なインスタンスメソッドとして持っていて、`Kernel` 自身は `Module` の
インスタンスであり、`Module` の `ancestors` には `Kernel` が入っている。だから
`Kernel.eval("1+1")` は `2` を返す。実際に走らせて確かめた（`Kernel.printf` だけが
`NoMethodError` になり、これは本当に無いメソッドだった）。

## 捨てた案

**集計とMarkdown生成を Ruby でやる。** 一覧を吐くのも突き合わせるのも同じ言語のほうが
気持ちがいいが、SabiRuby にファイル IO が無い（no_std で、mruby-io は移植対象外）ので
2 つの一覧を読み込めない。ホストの `ruby` や `python3` に頼る手もあり、`tools/gen_opcode.py`
という前例もあるが、`tools/mrbtest.sh` が awk で後処理している以上、依存を増やさず awk に
揃えるのが筋だと判断した。結果、`tools/coverage.rb` は「吐くだけ」、突き合わせと Markdown は
`tools/coverage.sh` の中の awk 1 本になった。

**gem 由来をメソッド単位で機械的に出す。** 計画書には「`Method#owner` と定義元のファイル名で
判定できる範囲で」とあったが、mruby には `Method#source_location` が無く、`Method#owner` は
クラスを答えるだけで gem は分からない。mrblib を読み込んだ順を VM が覚えているわけでもない。
諦めて、クラス → gem の表を `tools/coverage.sh` の awk の `BEGIN` に手で置き、
「これは手で持っている唯一のデータだ」と生成物の中に書くことにした。副作用として、
コアクラスにメソッドを足す gem は列に出ない（`Kernel.gets` は mruby-io、`Kernel.printf` は
mruby-print だが、どちらも core と表示される）。これも文書に明記した。

## 踏んだ罠

awk は出力先のファイルに 1 行も書かないとファイルを作らない。可視性を数えるようにして
`modfunc_sabiruby.txt` が 0 件になったとき、前回の実行で書いた 10 行がそのまま残り、
見出しは「0 more」なのに 10 行並ぶ、という文書ができた。リストのファイルは awk を呼ぶ前に
`: >` で空にするようにした。`touch` では消えない。

生成が再現するかは、2 回続けて走らせて `diff` が空になることで確かめた（awk の
`for (k in array)` の順序は不定なので、出力は全部 `sort` を通してある）。
`MRUBY_BIN` を渡す経路（Docker を使わず手元の `mruby` を使う）も、docker を呼ぶだけの
ラッパを `MRUBY_BIN` に渡して同じ文書が出ることを確かめた。

## 出た数字

| | クラス・モジュール | メソッド |
|---|---:|---:|
| SabiRuby | 70 | 1345 |
| 本家 4.1.0-rc | 224 | 1545 |
| 両方 | 64 | 1188 |
| SabiRuby だけ | 6 | 157 |
| 本家だけ | 160 | 357 |

本家だけの 357 の内訳は、POSIX の gem 312、モジュール関数の片割れ 3、持ち主違い 20、
**本当に答えないもの 22**。SabiRuby だけの 157 は、片割れ 0、持ち主違い 39、**追加 118**。
追加 118 の内訳は Task / Task::Queue が 37、CMath が 34（モジュール関数なので public な
インスタンスと特異の両方に出る）、`require`/`load` とその補助が 10、GC のつまみが 4、
mruby-sleep が 4、mruby-print の `__printstr__` が 2 で、ここまでの 91 はすべて
「本家の gembox に無いものを持っている」ことの言い換えだった。残る 27 が、同じ土俵での
追加（`Module#public_method_defined?` の類、`Exception#full_message`、`Integer#pred`、
`Symbol#id2name`、`Time#strftime`、`Numeric#step`、`Rational#truncate`、
`Array#__ary_eq` のような内部用）。

本当に無い 22 のうち、目に付くのは `Hash#default_proc=`（getter はあるのに setter が無い。
`h.default_proc = proc {}` は `NoMethodError`）、`Numeric#fdiv`（`Integer#fdiv` と
`Float#fdiv` はあるので、Ruby で書いた `Numeric` の子だけが困る）、`Module#const_added` と
`Module#method_undefined` と `BasicObject#singleton_method_added` / `_removed` /
`_undefined`（定義フック）、`Kernel#printf` / `putc`（`docs/plans/leftovers-plan.md` が
既に拾っている）。残りの `Kernel#gets` / `open` / `readline` / `readlines` は mruby-io なので
移植対象外だが、クラス単位の gem 表では `Kernel` = core なので落とせず一覧に残っている。

## 残していない確認

Rust には触っていないので `cargo test --workspace` は走らせていない（`git status` に
`.rs` の変更が無いことは確かめた）。`RUBY_ENGINE` は両方の VM で `"mruby"` を答えるので、
生成物からは engine を見分けられない。文書には両方の `MRUBY_DESCRIPTION` を並べて、
これは項目 5 の宿題だと書いてある。
