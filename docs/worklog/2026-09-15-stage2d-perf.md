## 1. 切り分け

`perf` はこの環境に無いので、これまでと同じく操作ごとの小さなスクリプトで測る
（スクラッチパッドの `micro/*.rb`、min of 5、`taskset -c 2`）。
Hash 系はすべて同じ形にした ―― 外 50,000 × 内 10 の二重ループで 50 万回、
本体だけを差し替え、ループだけの版（`h00_loop` 22.7 ms）を引いて 1 回あたりに直す。

### 1.1 Hash の 16 要素以下の固定費は何でできているか

| 切り分け | ms | ループを引いて 1 回あたり |
|---|---:|---:|
| `h00_loop` ループだけ（`s += j`） | 22.7 | — |
| `h12_ary_get10` `s += a[j]`（10 要素の Array） | 36.5 | **27.6 ns** |
| `h13_ary_size` `s += a.size` | 40.9 | 36.4 ns |
| `h14_ruby_call` `s += r.get(j)`（Ruby のメソッド） | 43.3 | 41.2 ns |
| `h01_get_int10` `s += h[j]`（10 要素、Integer 鍵） | 44.6 | **43.9 ns** |
| `h04_set_int10` `h[j] = j`（既存の鍵） | 38.5 | 31.7 ns |
| `h06_key_int10` `s += 1 if h.key?(j)` | 54.6 | 63.9 ns |
| `h08_aref_only` `s += 1 if ks[j]`（下の 2 つの土台） | 36.3 | 27.3 ns |
| `h07_get_sym10` `s += h[ks[j]]`（Symbol 鍵） | 57.4 | 42.1 ns（土台を引く） |
| `h09_get_str10` `s += h[ks[j]]`（14 バイトの String 鍵） | 62.4 | **52.2 ns**（同上） |
| `h10_set_str10` `h[ks[j]] = j`（String 鍵、既存） | 111.9 | **151.2 ns**（同上） |
| `h11_get_obj10` `s += h[ks[j]]`（`hash`/`eql?` が Ruby） | 179.3 | **285.9 ns**（同上） |

読み方はこうなる。

* **ネイティブ呼び出しと引数の受け渡しだけで 28 ns**（`Array#[]`、引数 1 個、中身はほぼ添字 1 回）。
  Ruby のメソッド呼び出し（41 ns）と大差ない。`docs/design/optimizations.md` 5 節が
  「固定費 90 ns（ネイティブ呼び出しと引数の受け渡し）」と書いていたが、**その 90 ns の中で
  呼び出しが占めるのは 3 分の 1 弱**で、残りは Hash 自身の仕事だった（下の 1.2）。
* **Hash に固有の仕事は Integer 鍵で 16 ns**（43.9 − 27.6）。内訳は `hash_sync`、`key_hash`、
  候補探し、`key_eql`。String 鍵では 24 ns（52.2 − 27.6）で、差の 8 ns が 14 バイトの FNV。
* **鍵の型で Ruby に戻るかどうかが桁を変える**。`hash` と `eql?` を Ruby で定義した鍵は 286 ns で、
  Integer の 6.5 倍。逆に言えば、計画書が段階 2d でやろうとしていた
  「`Integer`/`Symbol`/`String` の鍵を Rust で答える早道」は **すでに入っていた**（`Vm::key_hash` と
  `Vm::key_eql`、`src/vm.rs:3529`〜`3556`）。`Value::Obj` でかつ `String` でないものだけが Ruby に戻る。
  本家の `mrb_hash_ht_hash_func` も同じ形（`MRB_TT_STRING` / `SYMBOL` / `INTEGER` / `FLOAT` だけ
  native、それ以外は `mrb_funcall_id(hash)`）なので、**この項目は着手不要**と判断した。
  `String#eql?` の再定義を見に行かない点も本家と同じ振る舞いになっている。
* **`h[k] = v` は String 鍵で 151 ns と、読みの 3 倍**。差の 99 ns は
  `Vm::hash_set`（`src/vm.rs:3591`）が毎回やっていること ―― 鍵の文字列を `to_vec()` で複製し、
  それを `str_new` でもう一度複製してヒープに置き、凍結し、さらに `hash_index` の中と
  そのあとで `key_hash` を **2 回**計算する。

### 1.2 隠れていた O(n): `hash_sync` が毎回すべての鍵を複製する

上の形のまま、**引く鍵は 0〜9 のまま**、ハッシュの要素数だけを変えて測った。
鍵 0〜9 は必ず `entries` の先頭 10 個に居るので、線形探索の距離は要素数によらず一定で、
16 要素を超えれば索引が引かれて O(1) になる。つまり**要素数に比例する分が残っていれば、
それは探索ではない**。

| 要素数 | ms | 1 回あたり | 10 要素との差 |
|---:|---:|---:|---:|
| 10 | 44.6 | 43.9 ns | — |
| 100 | 55.9 | 66.4 ns | +22 ns |
| 1000 | 206.2 | 366.9 ns | **+323 ns** |

1 要素あたり 0.32 ns できれいに伸びている。犯人は `Vm::hash_sync`（`src/vm.rs:3558`）:

```rust
let (need, keys): (bool, Vec<Value>) = match &self.heap.get(o).kind {
    ObjKind::Hash(hd) => (hd.hashes_stale(), hd.entries().iter().map(|e| e.0.get()).collect()),
    _ => (false, vec![]) };
if !need { return Ok(()); }
```

`need` が偽でも `keys` を作ってしまう。つまり **Hash の探索 1 回ごとに、全要素の鍵を `Vec` に複製している**。
段階 2c で索引を入れて探索を O(1) にしたのに `ds_hash` が −19.8% しか動かなかったのは、
探索と並んでこの O(n) が残っていたからだった。`vm_optimization_bench` の中の
`hash_ops`（5 万要素）はこれで 1 回の引きにつき 5 万要素の複製をしていることになる。

### 1.3 `items()` の複製は、この 3 本ではもう効いていない

| 切り分け | ms | 中身 |
|---|---:|---|
| `a00_loop` ループだけ（1300 × 2000） | 104.6 | — |
| `a01_push` `a.push(j)` | 220.0 | 44 ns/回 |
| `a02_aset` `a[j] = a[j] + 1` | 213.2 | 42 ns/回（ネイティブ 2 回） |
| `a03_each` `a.each { |x| s += x }` | 443.9 | 131 ns/要素 |
| `a05_dup` `a.dup`（10000 要素 × 300） | 5.0 | 16.7 µs/回 |
| `a06_eq` `a != b`（10000 要素 × 300） | 6.3 | 21 µs/回 |
| `l01_build` `(1..10000).to_a` + `dup` × 300 | 7.6 | |
| `l02_shift_push` `while !li2.empty? ; li3.push(li2.shift) ; end` | 564.7 | 188 ns/回（ネイティブ 3 回＋ループ） |
| `l03_pop_push` `until li3.empty? ; li2.push(li3.pop) ; end` | 444.7 | 148 ns/回 |
| `l04_tail` `reverse!` / `!=` / `length` × 300 | 4.8 | |

`ds_array`（899 ms）は `push` 220 + `[]=` 213 + `each` 444 でほぼ全部で、**`items()` の複製は 1 つも通らない**
（`Array#[]` は添字の早道、`[]=` は段階 2c で `ary_len` に直した、`each` は mrblib の Ruby で `self[i]`）。
`bm_so_lists`（1005 ms）も `l02` + `l03` で 1010 ms、つまり `empty?`・`push`・`shift`・`pop` の
**ネイティブ呼び出しの回数そのもの**で、複製する `dup` と `!=` は合わせて 11 ms（1%）しかない。
`app_json_hash` も配列は `["a","b","c"]` の生成と `.size` だけ。

つまり計画書の「`ds_array` と `bm_so_lists` と `app_json_hash` で `items()` の複製がどれだけ効いているか」への
答えは **「この 3 本ではもう効いていない」**。段階 2c で長さだけを見ていた 8 か所を直した時点で、
ベンチに出る複製は無くなっていた。

残っているのは**ベンチに出ない側**で、こちらには質の悪いものがある。`ext_array.rs` の
`include?` / `member?` / `__count` は、ループの**中**で `items(vm, s)` を呼び直しているので O(n²) になる:

| 切り分け | ms | 1 回あたり |
|---|---:|---:|
| `a04_include` `a.include?(j)`（10 要素、50 万回） | 79.9 | **114.4 ns** |
| （比較）`h01_get_int10` `h[j]`（10 要素） | 44.6 | 43.9 ns |

10 要素で 114 ns、100 要素なら 10 倍以上になる形。ベンチには出ないが、ホストから渡された配列を
`include?` で引くのは実アプリでは普通なので、直す価値はある（下の 3 節）。

### 1.4 `app_json_hash` は 4 分の 3 が「作る」側

| 切り分け | ms |
|---|---:|
| `j01_build` 入れ子の Hash/Array/String を作るだけ（200 行 × 2300） | 924.1 |
| `j02_walk` 作ったものを読むだけ（同じ回数） | 377.5 |
| `j03_interp` `"item-#{i}"` と `.size` だけ（46 万回） | 107.7 |

`app_json_hash` 全体 1248 ms のうち 924 ms が構築側で、その中身は
**String 鍵の `hash_set`（1.1 の 151 ns）を 1 行あたり 6 回**払っている。
2 要素のハッシュリテラル 1 個で 371 ns。

## 2. 何をやるか（切り分けの結論）

1. **`hash_sync` の O(n)**（1.2）。これが段階 2d でいちばん大きい。
2. **`hash_set` の二度手間**（1.1）。`key_hash` を 2 回計算している。String 鍵の複製も、
   すでに在る鍵なら要らない。
3. **`items()`**（1.3）。ベンチに出る 3 本では効かないと分かったので、O(n²) になっている
   読むだけのネイティブ（`include?` / `member?` / `__count`）だけを直し、効果は
   micro ベンチで示す。ベンチ 22 本では「ぶれの範囲」になるはず。
4. **`vm_optimization_bench` の分類分け**。

# 3. 変更 1: `hash_sync` が毎回すべての鍵を複製しない

## 直したもの

`Vm::hash_sync`（`src/vm.rs:3558`）は「ハッシュ値が entries とずれていたら作り直す」だけの関数で、
探索（`hash_index`）の先頭から必ず呼ばれる。ずれているのは `replace` / `merge` / `dup` のように
**entries をまとめて入れ替えたあと**の 1 回だけなので、ほとんどの呼び出しでは何もしない。
ところが「何もしない」と分かる前に、`hd.entries().iter().map(|e| e.0.get()).collect()` で
全部の鍵を `Vec<Value>` に取り出していた。タプルの両側を 1 つの `match` で作ってから
`if !need { return }` していたので、`need` が偽でも複製は起きる。

直しは、聞く順番を入れ替えるだけ:

```rust
if !matches!(&self.heap.get(o).kind, ObjKind::Hash(hd) if hd.hashes_stale()) { return Ok(()); }
let keys: Vec<Value> = match &self.heap.get(o).kind { ObjKind::Hash(hd) => …collect(), _ => return Ok(()) };
```

借用は 2 回になるが、2 回目は「本当に作り直すとき」だけ通る。

**なぜ気づかなかったか**が本の素材になると思う。このコードは段階 2b で「走査のループが 1 要素ごとに
`heap.get(o)` を取り直していた」のを直したときに書かれたもので、狙いは**借用の回数を減らすこと**だった。
`match` を 1 つにまとめると借用が 1 回で済む ―― その形にしたときに、複製が条件の外に出た。
「借用を減らす」は正しい方向だったが、**減らした借用の中で O(n) の仕事をしていた**。
段階 2c の索引が `ds_hash` を 19.8% しか動かさなかったのも、これが残っていたからで、
索引を入れたあとに「まだ O(n) が残っていないか」を要素数を変えて測り直していれば、その日に見つかっていた。

# 4. 変更 2: `hash_set` が鍵を 1 回だけハッシュし、要るときだけ複製する

## 直したもの

`Vm::hash_set` は 1 回の `h[k] = v` で鍵に 3 つの仕事をさせていた。

1. 鍵が凍っていない String なら、**必ず**複製して凍らせる（`to_vec()` で 1 回、`str_new` の中でもう 1 回、
   計 2 回の複製と 2 回の割り当て）。
2. `hash_index` を呼ぶ（この中で `key_hash`）。
3. 戻ってきてから `key_hash` を**もう一度**呼ぶ（`push_entry` に渡すため）。

3 は無駄で、しかも鍵が `Object` なら `hash` という **Ruby のメソッドを 2 回呼ぶ**ことになる（1.1 節で測った
286 ns の鍵はこれを 2 回払っていた）。1 は、**すでに在る鍵に上書きするだけなら要らない** ――
その場合は既存の鍵がそのまま残り、作った複製は捨てられるだけだから。

順番を変えた。同期 → ハッシュ（1 回）→ 探索 → 見つかれば値だけ差し替え、無ければ**そこで**鍵を複製して追加。
探索を「すでにハッシュ済みの鍵」で行う入口 `hash_index_at(o, k, kh)` を切り出し、`hash_index` はその薄い皮にした。
複製も `to_vec()` した `Vec` をそのままヒープに置く形にして、2 回の複製を 1 回にした。

**なぜ複製を後ろに回してよいか**: String の鍵は `Vm::eql` でも `Vm::value_hash` でも**バイト列で**答える。
凍った複製と元の文字列は同じハッシュ値を返し、`eql?` でも等しいので、探索を元の鍵で行っても
結果は変わらない。追加のときだけ複製すればよい。

## 本家との突き合わせ

鍵の扱いを 1 本のスクリプトにして本家（`kishima/mruby:4.1.0-rc`）と突き合わせた
（凍った鍵・凍っていない鍵、`keys[0].equal?`、鍵にした文字列をあとから `<<` で伸ばす、
同じ内容の鍵での上書き、Integer/Symbol/Float/nil/true/false/String の混在、`delete`、
`replace`/`dup` のあとの引き、40 要素（索引あり）の `dup` と `delete`）。
**`hash` と `eql?` の呼ばれた回数以外はすべて一致**した。

その回数はこうなる。

| | 本家 | `b627d0a` | この変更 |
|---|---:|---:|---:|
| `h[k] = v`（新しい鍵）で `hash` が呼ばれる回数 | 0 | 2 | **1** |
| そのあと `h[k2] = v`（`eql?` で同じ鍵）で `hash` | 0 | 2 | **1** |

本家が 0 なのは、16 要素以下では AR（配列）表現を使い、**ハッシュ値をまったく使わない**から
（`eql?` だけで線形に探す）。SabiRuby は 16 要素以下でも `hashes` を持つ設計なので 0 にはならないが、
2 回払う理由は無かった。`eql?` の回数は変更前後で同じ（本家より 1 回多い箇所が 1 つあるが、
これは `b627d0a` からの既存の差で、この変更とは無関係）。

# 5. 変更 3: 中身を読むだけのネイティブが配列を複製しない

## どこを直したか（そして、どこを直さなかったか）

1.3 節の切り分けどおり、計画書が名指しした 3 本（`ds_array`、`bm_so_lists`、`app_json_hash`）には
`items()` の複製がもう通っていない。段階 2c で「長さだけが欲しい 8 か所」を直した時点で、
ベンチに出る複製は消えていた。だから**ベンチを速くする目的では直すところが無い**。

残っていたのは、ベンチが踏まない側の、質の悪い 3 つ。`ext_array.rs` の `include?` / `member?` と
`__count`（`Array#count(obj)` の実体）は、こう書かれていた:

```rust
let mut i = 0;
loop { let list = items(vm, s); if i >= list.len() { break; } if vm.equal(list[i], a[0])? { … } i += 1; }
```

**ループの中で `items(vm, s)`**、つまり 1 要素ごとに配列全体を `Vec<Value>` に複製する。O(n²)。
毎回読み直しているのは意図的で、`==` が Ruby でありうる以上、その間に配列が縮んだり差し替えられたり
しうるから正しい ―― **読み直しは要るが、複製は要らない**。1 要素だけ取ればよい:

```rust
let it = match vm.ary(s).and_then(|l| l.get(i).map(|x| x.get())) { Some(v) => v, None => break };
```

`Vm::ary` は `&[Slot]` を貸すだけなので割り当てが無く、`vm.equal` を呼ぶ前に借用は切れている。
同じファイルの `index` / `rindex` が最初からこの形だったので、それに合わせただけとも言える。
`array.rs` の `include?` / `member?`（gem が上書きする前の定義）も、1 回の複製をしていたので同じ形にした。

**直さなかったもの**: `each` / `map` / `inject` / `join` / `inspect` / `sort` / `sum` / `__max` / `__min` など、
1 回だけ複製してから回るもの。複製は O(n) で、そのあとの仕事も O(n) なので次数が変わらず、
ブロックや `<=>` が配列を書き換えたときの振る舞いを変えてしまう恐れがある（複製を回っている今は
「開始時点の配列」を回り、添字読みにすると「今の配列」になる）。ここは**振る舞いの選択**であって
速度の話ではないので、この段階では触らない。計画書の「効くものだけ」に従う。

## 数値

micro（交互、min of 5、A = 変更 2、B = 変更 3）:

| 切り分け | A ms | B ms | 変化 |
|---|---:|---:|---:|
| `a04_include` `a.include?(j)` 10 要素 × 50 万回 | 80.4 | 63.6 | **−20.9%** |
| `a07_include100` 同じく 100 要素 | 174.4 | 64.5 | **−63.0%** |
| `a08_count` `a.count(j)` 100 要素 × 20 万回 | 1004.4 | 137.7 | **−86.3%** |
| `h00_loop` 配列を触らないループだけ | 22.6 | 24.7 | +9.3% |

要素数への依存が消えている（100 要素の `include?` が 10 要素と同じ 64 ms になった）。

ベンチ 22 本（交互 A/B、`bench/results/ab-hashset-items.tsv`）:

| 分類 | A ms | B ms | 変化 |
|---|---:|---:|---:|
| 実アプリ寄り | 8594 | 8631 | +0.4% |
| データ構造 | 2537 | 2544 | +0.3% |
| 命令ループ | 14614 | 14972 | +2.5% |
| 呼び出し | 3583 | 3603 | +0.6% |
| メモリ | 1978 | 1978 | −0.0% |
| **全体** | **31306** | **31729** | **+1.3%** |

**全体が +1.3%、つまり遅くなっている**。ここは正直に書く価値がある。動いたのは
`loop_while_add` +8.7%、`loop_times` +7.8%、`bm_so_mandelbrot` +7.2% の 3 本で、残り 17 本は ±2% 以内。
そして `grep` で確かめたとおり、**ベンチ 22 本のどれ 1 つとして `include?` / `member?` / `count` を呼んでいない**。
呼ばれないコードが実行時間を変えることはないので、これはコード配置の揺れ。
同じ 3 本が、この段階の 3 回の計測で

| | 変更 1 | 変更 2 | 変更 3 |
|---|---:|---:|---:|
| `loop_while_add` | +6.6% | −5.7% | +8.7% |
| `bm_so_mandelbrot` | +13.0% | −7.5% | +7.2% |

と行ったり来たりしている。`docs/design/optimizations.md` 4 節の「呼び出しを含まないベンチは
候補ごとに ±4〜12% 動く」のとおりで、best と median の差はどれも 1% 以内（静かな窓で取れている）。

**取り込むかどうかで迷った。** 段階 2 の規則は「効かない、または遅くなる変更は取り込まない」。
この変更はベンチの合計で +1.3% だが、(1) ベンチはこのコードを 1 回も実行しない、
(2) 変更したメソッド自身は 100 要素で 3〜7 倍速い、(3) O(n²) が O(n) になった（次数が下がった）、
(4) 本家と出力が一致する（下）。**取り込む**判断にしたが、コミットは 1 つに切ってあるので、
本体が「ベンチの合計を優先する」と判断すればこのコミットだけ落とせる。

# 6. 変更 4: `vm_optimization_bench` を 5 つに割る

## なぜ

`vm_optimization_bench` は本家の `benchmark/vm_optimization_bench.rb` をそのまま持ってきたもので、
`measure` で 35 個の計測を順に回す。分類は「命令ループ」だったが、中身は
ディスパッチ・算術・メソッド呼び出し・Array/Hash の添字・ループの形・定数の読み込み・分岐予測・
レジスタ圧・複合（fib、tak、配列操作、文字列操作、**5 万要素の Hash**）と、分類 5 つ全部にまたがっている。
段階 2c の索引が「命令ループ −11.8%」に出たのも、この 1 本の中の `hash_ops` が動いたからで、
**分類の名前が中身を説明しなくなっていた**（段階 2c の worklog の最後にもそう書かれている）。

## どう割ったか

本家のセクション区切りに沿って `bench/src/vmo_*.rb` の 5 本にした。`measure` の定義と各ブロックの
中身は**本家のまま 1 行も変えていない**（`N`、`M`、warm up 3 回、iterations も同じ）。
