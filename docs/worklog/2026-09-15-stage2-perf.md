## 候補 0: `Op::from_u8` の表引きをやめる

**読んだところ**: `src/opcode.rs:257`（段階 0 が入れた `OP_TABLE.get(b as usize).copied()`）、
`src/vm.rs:2785`（実行ループで毎命令呼ぶ唯一の熱い場所）、`tools/gen_opcode.py`。
`from_u8` を呼ぶ場所は全部で 5 つ（`vm.rs:2785`、`rite.rs:374,383`、`inspect.rs:343`、`mrbtest.rs:426`）だが、
熱いのは `vm.rs` の 1 つだけ。

**仮説**: `Op` は `#[repr(u8)]` で 119 個の variant を持つので、`Option<Op>` は niche 最適化で 1 バイトに収まり
（`None` は 119）、`match b { 0 => Some(Op::Nop), … , _ => None }` は「119 未満ならそのまま、そうでなければ 119」
という範囲チェック 1 回に畳める見込みがある。表引きは畳めない（`OP_TABLE` から毎回 1 バイト読む）。

**やったこと**: `tools/gen_opcode.py` に `from_u8` を 119 本の `match` として出力させ、
`OP_TABLE` の生成をやめた（`from_u8` 専用の表で、他に使い手はいない）。`opcode.rs` は生成物なので手では直さず、
`python3 tools/gen_opcode.py ../../ref/mruby/include/mruby/ops.h > src/opcode.rs` で作り直した。
差分は 2 か所だけ（`from_u8` の本体と `OP_TABLE` ブロック）で、`Op` の variant・`OP_NAMES`・`OP_OPERANDS` は 1 バイトも動いていない。

**生成コードを先に確かめた**（測る前に）。`objdump -d` で `exec_frames` を比べると、狙いどおりだった。

変更前（表引き）:

```
cmp    $0x77,%r11b            ; 119 未満か
jae    <bad opcode>
lea    <OP_TABLE>,%rcx
movzbl (%r11,%rcx,1),%edx     ; ← 読み出し 1: OP_TABLE[byte] → op
lea    <OP_OPERANDS>,%rcx
movzbl (%rdx,%rcx,1),%edx     ; ← 読み出し 2: OP_OPERANDS[op]
movslq <jump table>(,%rdx,4),%rcx
jmp    *%rcx
```

変更後（`match`）:

```
cmp    $0x77,%r11b
jae    <bad opcode>
lea    <OP_OPERANDS>,%rcx
movzbl (%r11,%rcx,1),%r9d     ; ← 読み出しは 1 つ。生のバイトで直接引いている
movslq <jump table>(,%r9,4),%rcx
jmp    *%rcx
```

`Op::from_u8` は完全に消え、範囲チェックだけが残った。`Option<Op>` が niche 最適化で 1 バイトに収まる
（`Op` は 119 variant なので 119〜255 が空き、`None` がそこに入る）ので、`match` は「119 未満ならバイトそのもの」
に畳める。段階 0 の表が足した「毎命令 1 バイトの読み出し」がちょうど 1 つ消えたことになる。

### ここで計測がひっくり返った（重要）

## 候補 3: `find_method` が `Method` を値で返すのをやめる

**読んだところ**: `src/vm.rs:1392`（旧 `find_method`）、`src/object.rs:36`（`Method`）、
呼び出し側 28 か所（`grep -rn find_method src/`）。熱いのは 2 つだけ ——
`op_send_vis`（`src/vm.rs:3549` 付近。バイトコードの SEND が通る道）と `funcall`（`src/vm.rs:1501`。
ネイティブから Ruby を呼ぶ道）。残り 26 か所は `alias`、`Method#unbind`、`respond_to?`、
`method_defined?` のような、1 回しか通らないところ。

**仮説**: `docs/bench.md` は段階 3 の +4.2%（fib）を「`Arc` を持つ variant が増えたので `#[derive(Clone)]` が
memcpy から分岐 + atomic 増加になった」と説明しているが、**atomic は `Closure` の腕でしか起きない**。
fib が呼ぶのは Ruby のメソッドなので `Method::Ruby` で、参照カウントには触らない。それでも 4% 落ちたのなら、
効いているのは分岐ではなく **drop glue** のはず。`Method` が `Arc` を持つ型になった時点で
`Option<(Method, ObjId)>` は「落とすときに判別子を見る値」になり、レジスタで返せなくなって、
スコープを抜けるたびに後始末のコードが要る。呼び出し 1 回につき 1 回これを作って捨てている。

**やったこと**: 探索の歩き方は 1 つに保ったまま、返り値を 2 通りにした。

* `find_method_entry(&self, class, mid) -> Option<(&Method, ObjId)>`（private）がクラスチェーンを歩く。
* `find_method` は今までどおり `Method` を clone して返す（冷たい 26 か所はそのまま）。
* `find_method_ref` は `MethodRef` を返す。`MethodRef` は `Copy` な enum で、
  `Ruby(ObjId) | Native(fn) | Closure | AttrReader(Sym) | AttrWriter(Sym)`。
  **`Closure` は中身を持たない** —— `Arc` を表に置いたままにして、実際に呼ぶ 1 か所だけが
  `closure_of(owner, mid)` でもう一度表を引いて `Arc` を取る。クロージャはホストが登録するもので
  内側のループには出てこないので、そこだけ引き直しても構わない。これで `MethodRef` に drop glue が付かない。
* `op_send_vis` と `funcall` を `find_method_ref` に。`Method::Undef` の腕は `MethodRef::of` が `None` を返す形に
  畳んだので、`op_send_vis` の `Method::Undef => unreachable!()` と `funcall` の
  `Some((Method::Undef, _)) | None` が要らなくなった（前者は到達不能、後者は `find_method` が
  もともと `Undef` を `None` にしていたので死んだ腕だった）。

**外れた枝**: 最初は `MethodRef::Closure(NativeClosure)` にしようとしたが、それでは `Arc` が入って
`Copy` にならず drop glue も残るので意味が無い。`#[derive(PartialEq)]` も付けていたが、
`Native(NativeFn)` があるので `unpredictable_function_pointer_comparisons` の警告が出た。
使っていなかったので外した（関数ポインタの比較は既存コードが `core::ptr::fn_addr_eq` でやっている）。

## 候補 1: 毎命令の `CallInfo` clone

**読んだところ**: `src/vm.rs:2800`（`let ci = self.ci.last().unwrap().clone();`）と、
そこから作った `ci` を使う 101 か所。内訳を数えると `ci.irep` **32 回**、`ci.target_class` 10、`ci.proc_` 9、
`ci.n` 4、`ci.kw` 4、`ci.mid` 3、`ci.base` 3、`ci.pc` 2。
つまり **ほとんどの命令が使うのは `irep`・`base`・`pc` の 3 つだけ**で、残りは
`Op::Getconst`、`Op::Getcv`、`Op::Super`、`Op::Call`、`Op::Def`、`Op::Karg` のような
めったに通らない命令しか見ていない。

`CallInfo` は 13 フィールド（`usize` 3 つ、`ObjId` 2 つ、`Option<Sym>`、`Option<ObjId>`、`Cci`、`Vis`、`u8`、`bool` 3 つ）で、
全部 Copy なので `clone()` は memcpy だが、**毎命令 56 バイトを `Vec` から読んでスタックに積んでいる**。

**やったこと**: ループの先頭で 3 つだけ取る。

```rust
let top = self.ci.len() - 1;
let (base, irep, mut pc) = { let ci = &self.ci[top]; (ci.base, ci.irep, ci.pc) };
```

`top` はもともとオペランド解読のあとで `self.ci.len() - 1` として作られていた（`self.ci[top].pc = pc` と
`Op::Jmp` 系で使う）ので、それを先頭に繰り上げただけ。残りのフィールドを見る命令は、その場で
`self.ci[top].target_class` のように読む。読む位置がフレームを push する前であることは 1 つずつ確かめた
（`Op::Blkcall` だけは `self.ci.push(CallInfo { … target_class: ci.target_class … })` と
push の引数の中で読んでいたので、借用が重ならないよう外に出す必要があった —— と思ったが、
`self.ci.push` の受け手は `self.ci`、引数は `self.ci[top]` の読みで、Rust の二段階借用が通した）。

ついでに 3 つのヘルパの引数を変えた:

* `read_b/read_s/read_w(&self, ci: &CallInfo, pc)` → `(&self, irep: IrepId, pc)`。
  中で `self.ireps[ci.irep]` していただけなので、渡すものが 56 バイトの参照から `usize` 1 つになる。
* `kidx(&self, ci: &CallInfo)` → `kidx_at(&self, i: usize)`。`&self.ci[top]` を借りたまま `self.kidx(...)` は呼べない
  （`&self` と借用が重なる）ので、添字を渡す形にした。他に呼び手はいない。
* `const_lookup(&mut self, ci: &CallInfo, s)` → `const_lookup(&mut self, target_class: ObjId, proc_: ObjId, s)`。
  同じ理由。`const_lookup_noraise` のほうは `builtins/kernel.rs` の `__defined_const?` が
  `*vm.ci.last().unwrap()` を渡しているので、`&CallInfo` のまま残した。

## 候補 2: 常時オンの `op_counts`

**読んだところ**: `src/vm.rs:2806`（`self.op_counts[byte as usize] += 1;`）、
`src/vm.rs:370`（`pub op_counts: Vec<u64>`）、読む側は 3 つ ——
`src/inspect.rs:341` の `op_histogram`（Playground の `sabi_op_counts`）、
`src/mrbtest.rs:418`（本家テストの「Opcodes executed: n / 119」）、`cli/src/main.rs:305`。

**仮説（外れた）**: 「`u64` を 1 つ足すだけなので、せいぜい 1% だろう。フラグ 1 つの分岐か feature か、
安いほうを選べばいい」。計画書もそう書いている。

**実測**: まず**天井**を測った —— 増分の行を消しただけのビルドと現状を比べる。

| ベンチ | 現状（`Vec`、常時） | 数えない | 差 |
|---|---:|---:|---:|
| `loop_while_add` | 1248.9 | 930.5 | **−25%** |
| `bm_so_mandelbrot` | 1948.9 | 1540.8 | **−21%** |

**1 命令 1 カウントが 2 割**。これは予想外だったので理由を考えた。`Vec<u64>` への
`self.op_counts[byte as usize] += 1` は、(1) `Vec` のデータポインタを読む、(2) `len` を読む、
(3) 範囲チェック、(4) `ptr + byte*8` を読む、(5) 足す、(6) 書き戻す。`&mut self` が動き回るので
(1)(2) は毎命令読み直しになる。そして (4)(6) は**同じアドレスへの読み書きが連続する**
（同じ命令が連続すればまったく同じ 8 バイト、違っても同じキャッシュライン）ので、
ストア→ロードの依存が毎回できる。1 命令 5 ns のループでは、この 1 本の依存鎖が 1 ns を占める。

そこで 4 通り作って、全部「数えない」ビルドを基準に測った（P コア固定、min of 15。
この日は機械が外から揺さぶられていたので、5 回では足りず 15 回の最小値を使った）:

| 版 | `loop_times` | `loop_while_add` | `loop_if_branch` | `bm_so_mandelbrot` | `call_args` |
|---|---:|---:|---:|---:|---:|
| `Vec` + 常時（現状） | — | +25% 相当 | — | +21% 相当 | — |
| `Vec` + フラグ（オフ） | +13.1% | **+26.2%** | +11.7% | **+30.9%** | +9.6% |
| 固定長配列 + 常時 | +3.5% | +6.5% | +9.0% | +8.3% | +14.4% |
| **固定長配列 + フラグ（オフ）** | **+2.9%** | **+2.6%** | **+3.5%** | **+6.7%** | **+4.9%** |

**一番の驚きは 2 行目**: 「`Vec` のまま、フラグで数えないようにする」と、
**数えるのをやめたのに、固定長配列で数え続けるより遅い**。`Vec` を残したままだと
ポインタと `len` の読み出しが消えず、そこにフラグの読み出しと分岐が足される。
計画書が想定した「分岐 1 回のほうが安いかもしれない」は、器を変えないまま分岐だけ足す形では成り立たなかった。

**採った形**: `op_counts` を `[u64; OP_COUNT]` の固定長配列にして `Vm` の中に直に置き、
**添字を生のバイトではなく解読後の `op as usize` にする**。`Op` は 119 variant なので
コンパイラは `op as usize < 119` を知っており、範囲チェックが消える。ポインタ読みも消える。
そのうえで `count_ops: bool` を足し、既定はオフ。`Vm::set_op_counting(bool)` / `Vm::op_counting()` を公開した。
`mrbtest::run_file_prelude` はカバレッジ行を出すので自分でオンにする。Playground は
`sabi_op_counts` を使うので、起動時にオンにする必要がある（`docs/playground.md` に注記した。
**Playground 側のコード変更が要る** —— このリポジトリには無い）。

feature（`stats`）は作らなかった。理由: CLI がその feature を既定で有効にすると、
ベンチが測るバイナリにコストが戻ってしまい、無効にすると `sabiruby mrbtest` の
「Opcodes executed」が出せなくなる。実行時フラグなら両方が成り立ち、しかも測ってみると
フラグ版（配列）と「そもそもコードが無い」版の差は 2.6〜6.7% しかない。

## 候補 4: メソッドキャッシュ

**読んだところ**: `src/vm.rs` の `find_method_entry`（クラスチェーンを歩き、節ごとに
`HashMap<Sym, Method>` を引く）、`src/object.rs` の `Heap::class_mut`、`Heap::alloc`、
それとメソッド表を書き換えている全部（`grep -rn "\.methods\b" src/`）。

**設計で一番怖かったのは速度ではなく無効化**。書き換えの入口は 40 か所以上ある
（`def_method`、`undef_method`、`remove_method`、`alias`、`define_method`、`include`、`prepend`、
`extend`、`initialize_copy`、`ext_metaprog.rs` の `Module#remove_method`、`ext_regexp.rs` が
`$~` 系を `Undef` で塞ぐところ、…）。1 つずつ「ここでキャッシュを捨てる」と書いて回ると必ず漏れる。

**通り道が 1 本しかないことを確かめた**: メソッド表・可視性・スーパークラス・`origin`・`iclass_of` は
すべて `ClassData` の中にあり、`ClassData` への可変アクセスは `Heap::class_mut` だけを通る
（`heap.get_mut(o).kind` を直に書き換えてクラスを触っている場所は無い —— `grep` で確認）。
そこで **`class_mut` の 1 行で世代番号を上げる**。「クラスに可変アクセスした＝答えが変わったかもしれない」
という粗い判定で、`@@x = 1` や定数代入でもキャッシュが飛ぶが、正しさは漏れない。

もう 1 つの穴は **`ObjId` の再利用**。GC が回収したクラスの番号が別のクラスに割り当て直されると、
(class, mid) の鍵が一致してしまう。`Heap::alloc` で `ObjKind::Class` を作るときにも番号を上げて塞いだ。
（`ObjId` が非クラスに再利用される場合は、`class_of(recv)` がその番号を返すことがないので問題にならない。
キャッシュに入っている `Method::Ruby(proc)` はメソッド表から GC の根で辿れるので生きている。）

**形**: 1024 行の直接マップ（1 way）。1 行は `(serial, class, mid, Option<(MethodRef, ObjId)>)` で、
`Box` に入れて `Vm` 本体は 8 バイトしか太らせない。見つからなかったことも覚える（`method_missing` が
繰り返し呼ばれる場合のため）。当たり判定は `serial` と鍵の比較だけで、外れたら今までどおり歩くので、
外れのコストは比較 3 回。`MethodRef` が `Copy` になっている（候補 3）から行をそのまま返せる。

### 無効化の確認

`tests/custom/method_cache.rb` を新設した（20 通り: 定義・再定義・`remove_method`・`undef_method`・
`include`・`prepend`・特異メソッド・`extend`・`define_method`・`alias`・`alias_method`・
include 済みモジュールへの後付け・`Object` への後付けとその上書き・「無い」をキャッシュしたあとの
`method_missing` 追加・クラスメソッドの再定義・`private` への変更・`class_eval`・`instance_eval`・
`Comparable` の `<=>` 差し替え・`Struct` のメンバの上書き）。**どれも「古い答えを 200 回呼んでキャッシュに載せてから」
変更する**のが肝で、そうしないとキャッシュを素通りしてしまう。

期待値は手で決めず、**本家 mruby 4.1.0-rc に同じスクリプトを食わせた出力**をそのまま使った
（`tools/custom.sh method_cache` が `.rc.out` を作り、`.expected` と一致）。SabiRuby の出力は
本家と 1 行も違わない。加えてキャッシュ導入前のバイナリとも `diff` して同一を確認した。

本家テスト 106 ファイルは baseline どおり。`SABIRUBY_GC_STRESS=1` でも `tests/custom` は通る
（割り当てのたびに GC が走るので `ObjId` 再利用の穴があれば出るはず）。

### 数値（交互 A/B、5 ラウンド、A = 候補 2、B = 候補 4）

`bench/results/ab-c2-c4.tsv`。

| 分類 | A ms | B ms | 変化 |
|---|---:|---:|---:|

| データ構造 | 6856 | 6746 | −1.6% |
| 命令ループ | 25316 | 25603 | **+1.1%** |

速くなった: `app_tak` **−10.0%**、`bm_fib` −7.1%、`ds_array` −6.0%、`mem_short_lived` −5.2%、
`mem_retained` −5.0%、`call_block_yield` −4.1%、`app_robot` −3.4%、`call_fiber` −3.1%、`call_args` −2.8%。
遅くなった: `bm_so_mandelbrot` +4.9%、`loop_while_add` +2.1%、`loop_if_branch` +1.4%、
`loop_times` +1.1%、`vm_optimization_bench` +0.8%。

遅くなった 5 本はどれも**送信がほとんど無い**ベンチで、キャッシュは通らない。
40 KB の表が L2 を押しているのかと思い、行数を 256 に減らして測り直したが、
`bm_so_mandelbrot` −2.2% と引き換えに `call_block_yield` +2.0%、`app_tak` +1.0% で、
どちらも ±2% の配置揺れの中だった。**1024 のまま**にした（当たり率のほうが読みやすい）。

**判断: 採る。** 全体 −1.3% は 4 候補で一番小さいが、内訳が計画書の狙い
（「呼び出し」と「実アプリ寄り」）に素直に乗っている。`app_tak` −10% と `bm_fib` −7.1% は
チェーンを歩いてハッシュを引く仕事がそのまま消えた分。

**見送った案**: 本家のような呼び出し場所ごとのインラインキャッシュ（irep の命令ごとに 1 行持つ）。
当たり率はこちらのほうが高いが、`VmIrep` に可変の配列を足すことになり、
ireps が `Vm` に共有されているぶん設計が大きくなる。計画書も「形は自由」と書いているので、
まず安いほうを測った。
