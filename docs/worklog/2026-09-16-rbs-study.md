# 2026-09-16 RBS で境界を宣言する（検討の段階）

`docs/plans/from-mrubyedge-plan.md` の 2 番。到達点は設計文書 1 本（`docs/design/rbs.md`）で、
実装はしない段階。作業は「読む → 実際に動かして確かめる → 書く」の順で、確かめたのは 3 つ
（crates.io の RBS 用 crate が手元でビルドできるか、`#[ruby_methods]` から RBS を機械的に出せるか、
出したものが本物の RBS か）。以下はその過程で、捨てた案と外した見込みを含む。

## 最初の見込みと、それが外れたところ

計画書は「逆向き（Rust から RBS を生成する）のほうが二重管理が無く筋がよい可能性。まずこちらを試す」
と書いていて、結論はそのとおりになった。ただし理由は計画書が想定したものとは少し違っていて、
決め手は「二重管理」ではなく **マクロが見ているのが解決済みの型ではなく型の綴りである** という点だった。

`macros/src/expand.rs` を読むと、`method_spec`（196 行）が `syn::ImplItemFn` から取り出しているのは
レシーバの種別、先頭の `&mut Vm` が文脈であること（`is_vm`、258 行）、引数の `(Ident, Type)` の並び、
Ruby 名と `#[ruby(skip)]` で、`sig.output` は読んでいない。`define`（270 行）が戻り値を
`IntoRubyRet` に投げるだけで済むからで、ここは `MethodSpec` に 1 フィールド足せば埋まる。
埋まらないのは型の解決で、`n: Hp`（`type Hp = i64`）は展開時には `Hp` という綴りでしかない。

この非対称が、検査（(a) の案）と生成の優劣を決めた。生成側は「知らない綴りは `untyped`」と倒せば
嘘をつかずに済む。検査側は知らない綴りを通すか落とすかしかなく、通せば検査にならず、落とせば
型エイリアスを書いた人が理由の分からないコンパイルエラーを見る。**同じ情報不足が、片方では
許容できる劣化になり、もう片方では機能を壊す。** これを見つけたので (a) は早い段階で落ちた。

## crates.io の RBS crate を実際にビルドしてみた

`cargo search rbs --limit 20` の 1 位は `rbs 4.8.4` だが、これは rbatis（ORM）のシリアライズ基盤で
無関係。RBS の crate は 3 つあった。

* `ruby-rbs` 0.3.0 / `ruby-rbs-sys` 0.3.0（2026-04-03、BSD-2、約 33k DL）。crates.io の
  `repository` が `https://github.com/ruby/rbs.git` で、**本家自身**が出している。
* `tree-sitter-rbs` 0.2.2（2025-11-13、第三者）。

`.crate` を展開して中を見ると、`ruby-rbs-sys` は rbs の C パーサ（`vendor/rbs/src/parser.c`、
`lexer.re`、`rbs_allocator.c` …）を丸ごと同梱して `cc` でビルドし、`bindgen` で束ねる作り。
`ruby-rbs` の `build.rs` は `vendor/rbs/config.yml` からノード型を生成する方式で、冒頭に
「ruby-prism の rust/ruby-prism/build.rs に着想を得た」と書いてある。API は
`ruby_rbs::node::parse(&str) -> Result<SignatureNode, String>`。

読んだだけで止めずにビルドを試したのは、`no_std` の VM にとって「C コンパイラが要るか」が
入れる／入れないの分かれ目だから。スクラッチパッドに空の crate を作って `cargo add ruby-rbs`
（依存 42 個が locked）、`cargo build`:

```
  thread 'main' panicked at bindgen-0.72.1/lib.rs:616:27:
  Unable to find libclang: "couldn't find any valid shared libraries matching:
  ['libclang.so', 'libclang-*.so', 'libclang.so.*', 'libclang-*.so.*'],
  set the `LIBCLANG_PATH` environment variable ..."
```

この機械には libclang が無い。`cc` は通ったが（`cargo:rustc-link-lib=static=rbs` まで出ている）、
bindgen で落ちる。つまり `ruby-rbs` を入れると、CI とこの repo を clone した人の機械に
libclang を要求することになる。VM の crate（依存 4 つ、`no_std` + alloc、thumbv7em と wasm32 を
CI でビルドしている）に入れる選択肢はこれで消え、入れるならホスト側の開発ツールに限る、という
線が引けた。**読まなくて済むなら読まない**という結論を、この 1 回のビルドが決めた。

## mruby/edge の `rbs_parser` は RBS ではなかった

`ref/mrubyedge`（`c7dd9ae`、2026-04-14）の `mrubyedge-cli/src/rbs_parser/mod.rs` は 328 行だが、
nom のパーサは 236〜328 行の約 90 行だけで、残りは Rust のコード生成（`args_decl`、`imported_body` …）。
文法は `def NAME: (T, T, …) -> T` の 1 形。メソッド名の `symbol`（263 行）は `[A-Za-z_][A-Za-z0-9_]*`
なので `alive?` すら書けず、型は裸の識別子だけ、意味づけのある型は引数側 4 つ（`Integer` / `Float` /
`bool` / `String`、それ以外は `unimplemented!` でパニック）。呼び出しは
`rbs_parser::parse(&s).unwrap()`（`subcommands/wasm.rs:170`、`:195`）。

ここで「これは RBS の小さい部分集合だ」と書こうとして、念のため本家で確かめた。この機械には
rbenv 経由で ruby 3.2.6 と `rbs` gem 3.6.1 が入っていたので、`hello.export.rbs` の中身
（`def hello: () -> void`）をそのまま食わせると:

```
$ rbs parse toplevel.rbs
toplevel.rbs:1:0...1:3: Syntax error: cannot start a declaration, token=`def` (kDEF)
```

**部分集合ですらなかった。** RBS のトップレベルに書けるのは宣言（`class` / `module` / `interface` /
定数 / `type`）で、`def` は `class … end` の中にしか置けない。mruby/edge の `.rbs` は RBS の見た目を
借りた wasm の IDL で、だから `ruby-rbs` に差し替えても互換にはならない（できるが `.rbs` の書き方が
変わる）。確かめる前に書いていたら文書に嘘が 1 行残っていた。

## 試作: `#[ruby_methods]` から RBS を出す

置き場所で少し迷った。proc-macro crate は**マクロ以外を公開できない**ので、`macros/src/` に
`pub fn rbs_of_impl` を足しても外から呼べず、`lib.rs` から使われないので dead_code になる。
feature の裏に置いて `#[ruby_methods]` に実際に生やさせる案もあったが、それは「この段階では実装しない」
に反する（既定オフでも生成コードが変わる）。結局 `macros/tests/rbs.rs` に全部入れた。
`syn` は `macros` の `[dependencies]` にあるので統合テストからも使える。`src/` は 1 行も変えていない。

やっているのは `syn::parse_str::<ItemImpl>` から、`expand.rs` と同じ規則で署名を読むこと
（レシーバの有無 → `self.` が付くか、先頭の `&mut Vm` を捨てる、`#[ruby(name)]` と `#[ruby(skip)]`）と、
`convert.rs` の `FromRuby` / `IntoRuby` の実装を全部並べた対応表。`Result<T, _>` と `VmResult<T>` は
`T` に潰す（RBS は例外を書かない）。戻り値なしと `-> ()` は `void`、引数位置の `()` は `nil`。

`macros/tests/player.rs` の `Player` を入れた出力:

```rbs
class Player
  def self.new: (Integer hp) -> Player
  def self.strongest: (Integer a, Integer b) -> Player
  def hp: () -> Integer
  def damage: (Integer n) -> void
  def rename: (String to) -> String
  def name: () -> String
  def alive?: () -> bool
  def greet: (untyped other) -> String
end
```

3 件のテストが通る（`cargo test -p sabiruby-macros --test rbs`）。予想より良かったのは引数名で、
Rust の `hp` / `n` / `to` がそのまま RBS の引数名として使えた（`(Integer hp)` は正しい RBS）。
エディタのホバーで効くのはここなので、これは拾い物。

予想より悪かったのは**クラス名**。`#[ruby(name = "Monster")]` は struct の `#[derive(RubyClass)]` 側に
あり、`impl Beast` からは見えない。試作では第 2 引数で手渡している。これが出力先の選択を決めた:
マクロが展開時にファイルを書く案（案 B）だとクラス名が取れないか、両方のマクロが同じ場所に
書き込む調整が要る。実行時の定数（案 A）なら `<Beast as RubyClass>::NAME` で取れる。
案 B はもともと `OUT_DIR` が proc-macro に無い・`cargo check` でも走る・増分ビルドのキャッシュを
壊す、という理由で不利だったが、クラス名の件で決まった。

出力が本物の RBS であることは `rbs` gem で確かめた。試作の 2 つの出力を `.rbs` に落として

```
$ rbs parse player.rbs shapes.rbs     # 何も言わずに exit 0
$ rbs -I . validate                   # 同じく
```

`Array[Integer?]`、`Array[String]?`、`[Integer, String]`（タプル）、`untyped`、`void` まで通っている。

## 落とした案

* **(a) マクロ時の型検査。** 上のとおり。RBS パーサが要る唯一の用途で、それが要らなくなった。
* **Playground の補完を今やる。** 効くのは組込みクラスの補完だが、そこには型が無い。
  `src/` の `define_fn` の出現 16 件はすべて `convert.rs` の rustdoc の中で、実際の定義は 0 件。
  組込みは `define_closure` / `define_method`（171 箇所）で、引数の型は `expect_int` などの
  本体の中にしかない。CRuby の core RBS を借りる案は、mruby との差（`Integer#/` の丸めなど）が
  そのまま嘘になる。ここは計画書 3 番（`coverage.md`）と組んで「名前だけの補完」が先。
* **手書きの部分集合パーサ。** 150〜250 行で書けるが、部分集合は「受け付ける」ことで嘘をつく。
  RBS を知っている人は `String | Symbol` を書く。読む必要が無い以上、書く理由も無い。
* **`Serde<T>` をレコード型（`{ hp: Integer }`）にする。** serde のデータモデルは
  `#[serde(rename / skip / flatten / tag)]` で変わり、それは `sabiruby-macros` から見えない。
  struct のフィールドをそのまま写すと嘘になるので `untyped`。正しくやるなら `sabiruby-serde` 側の
  derive から出すしかなく、別の仕事。

## rubevy の `ask`

`rubevy/docs/host-api.md` と `rubevy/src/lib.rs` を読んで、`Arg` は 3 つ（`Num` / `Text` / `Entity`）、
`Answer` は 7 つ（`Nil` / `Bool` / `Num` / `Text` / `List(Vec<f64>)` / `Rows(Vec<Vec<f64>>)` / `Entity`）
と、語彙が閉じていることを確かめた——と思ったが、`answer_value` / `publish_value` はクロージャの中で
VM に値を直接組めるので閉じていない。rubevy 自身が予約している 4 つの kind
（`RESERVED_KINDS`、`src/lib.rs:998`）のうち `component.get` がまさにそれで、Hash を返す。

結論として、ここに無いのは「型の書式」ではなく「宣言する場所」。宣言さえあれば実行時の検査も、
知らない kind の即時エラーも、`Rubevy::Proxy#respond_to_missing?` が本当のことを言うことも、
文書も補完も落ちてくる。RBS はその最後の 1 つの出力形式でしかない。rubevy の repo の仕事なので、
設計文書には表だけ置いて、次の段階の候補として書いた。
