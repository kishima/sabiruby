# 2026-09-16 `sabiruby-serde`（`from-mrubyedge-plan.md` の 1）

`docs/plans/from-mrubyedge-plan.md` の項目 1。`serde/` を新しいワークスペースメンバとして足し、
`to_value` / `from_value`、`Serde<T>`、Ruby の `JSON` を作った。ブランチ `serde`（main `70f9e9f` から）。

## まず読んだところ

`src/convert.rs` を頭から。`FromRuby`（`from_ruby(&mut Vm, Value) -> VmResult<Self>`）と
`IntoRuby`（`into_ruby(self, &mut Vm) -> Value`、**失敗できない**）、その上に `IntoRubyRet<M>` と
`RubyFn<M>` が乗っていて、`define_fn` はマーカ型 `M` の推論で関数の形を見分けている（`src/convert.rs:300`
あたりの `RetValue` / `RetVmResult` / `RetString` / `RetStr`）。この「マーカで曖昧さを消す」設計が、あとで
`Serde<T>` の返り側を決めるときに効いてくる。

値を作る側は `Vm::str_new` / `ary_new` / `hash_new` / `hash_set` / `bint_value`（`src/vm.rs:986` 以降）。
読む側は `str_bytes` / `ary_vals` はあるのに、**Hash を丸ごと読む入口が無い**。`hash_get` は鍵が要り、
鍵の一覧を得る手段が無い。ここは段階 3b（rubevy が `vm.heap` に手を伸ばしていた 4 か所を入口にした）と同じ穴
なので、`Vm::hash_entries(v) -> Option<Vec<(Value, Value)>>` を `ary_vals` の隣に足した。
`JSON::ParserError` を `JSON` の下に置くのにも入口が無かった（`define_class` は必ず `Object` の定数にする）ので、
`mrb_define_class_under` にあたる `Vm::define_class_under` も足した。コア側の追加はこの 2 本だけ。

GC は `docs/design/gc.md` を読んで確認した。`gc_maybe` の呼び出し元は `src/vm.rs:3145` の 1 か所、
実行ループの命令境界だけで、`heap.alloc` は GC を起こさない。つまりホストから `to_value` を呼んでいる間も、
ネイティブの中から呼んでいる間（`native_active >= 1`）も、Rust のローカルに持っている途中の `Value` は回収されない。
シリアライザが Array/Hash の中身を `Vec<Value>` に溜めてから一度に作る形にしてあるのは、この保証の上に乗っている。
`convert.rs` の `Vec<T>: IntoRuby` と同じ立場なので、rustdoc にも同じことを書いた。

## エラー型をどうするか

計画書は `to_value(&mut Vm, &T) -> VmResult<Value>` と書いているが、serde の
`ser::Error` / `de::Error` は `fn custom(msg: impl Display) -> Self` を要求する。`VmError::Raise` は
**例外オブジェクト**を持つので、`&mut Vm` 無しには作れない。`VmError` を serde のエラー型にすることはできない。

そこで `sabiruby_serde::Error { Message(String), Vm(VmError) }` を作り、`to_value` / `from_value` の
境界で `into_vm_error(&mut Vm) -> VmError` に変換することにした。`Message` は `TypeError`
（`FromRuby` が同種の間違いに投げるのと同じクラス）、`Vm` はそのまま再送出。これで計画書の形（`VmResult`）を保ったまま
serde の要求も満たせる。公開はしてある（`Serializer` を自分で回す呼び手には見える）が、普通は目にしない。

`describe_error` の出力が `"TypeError: msg"` だと思い込んでテストを書いて落ちた。実際は
`"msg (TypeError)"`（本家の `mrb_print_error` の形）。テスト側を直した。

## `Serde<T>` の返り側 — 二択で、両方は書けない

`FromRuby` 側は素直（`VmResult` を返せる）。問題は `IntoRuby` で、`into_ruby` は `Value` を返すだけで
raise できない。最初は「`IntoRuby` を実装せず、`IntoRubyRet<新しいマーカ>` を `Serde<T>` に実装すれば
`define_fn` から失敗を raise にできる」と考えた。**これは書けない。** `impl<T: IntoRuby> IntoRubyRet<RetValue> for T`
がすでにあるので、`Serde<T>: IntoRuby` と新マーカの impl が両方あると、`define_fn` の呼び出し側で `M` の推論が
曖昧になってコンパイルが通らなくなる。つまり `IntoRuby` を実装するか、`IntoRubyRet` を実装するかの二択。

指示どおり `IntoRuby` を採った。失敗したときに何を返すかで迷い、

* `nil` を返す → `Option::None` と見分けがつかない。黙って壊れる。
* panic する → VM の中で panic はホストを落とす。論外。
* **例外オブジェクトそのものを返す** → `vm.is_exception(v)` で見えるし、Ruby 側では `raise v` できる。

3 番目にした。そもそもこのクレートのシリアライザ自身は VM が失敗しない限り失敗しない（鍵は String か Symbol なので
`hash_set` の `key_hash` が Ruby を走らせることも無い）ので、この経路に入るのは手書きの `Serialize` が
`Error::custom` を呼んだときだけ。rustdoc にそう書き、テスト（`a_serialize_that_fails_answers_with_the_exception_rather_than_with_data`）で
その 1 例を押さえた。ちゃんと raise したい関数は `VmResult<Value>` を返して `to_value` を自分で呼べばよい、とも書いた。

## CRuby との突き合わせで出た唯一の食い違い: 鍵の順序

`serde/tests/custom/json_roundtrip.rb` を CRuby 3.2.6 で流して `.expected` を作り、同じ `.rb` を
SabiRuby で走らせた。31 行のうち **1 行だけ**違った。

```
CRuby     {"sym":1,"2":"two"}
SabiRuby  {"2":"two","sym":1}
```

`serde_json::Map` は既定で `BTreeMap` で、鍵が整列される。Ruby の Hash は挿入順を保つ（`HashData` の
`entries` はそもそも挿入順の `Vec`）ので、ここは埋めなければ嘘になる。`serde_json` の `preserve_order`
feature を入れると `IndexMap` になって直るが、その feature は `std` を含んでいる（serde_json の Cargo.toml:
`preserve_order = ["indexmap", "std"]`）。

クレート全体を `std` にするのは避けたかったので、`json` feature（既定オン）を作って `serde_json` を
optional にし、変換層だけなら `no_std` + alloc のままにした。`cargo build -p sabiruby-serde
--no-default-features --target thumbv7em-none-eabi` が通ることを確かめてある。
これは計画書に無い分岐だが、「`sabiruby` 本体は serde に依存しない（`no_std` と依存の小ささを保つ）」という
計画書の趣旨をこのクレート自身にも適用した形。

ついでに、この食い違いが見つかったのは `.rb` のパース側の鍵がたまたま辞書順（`a b e f g`）だったからで、
気づいたあとで入力の鍵の順を `g a f b e` に入れ替えて、`h.keys` が文書の順で返ることも見るようにした。

## 落ちたところ、直したところ

* **`2**64` の往復が落ちた。** `BigInt` から i128 を取るのに `to_i64()` → `to_u64()` の順で試していたが、
  `2**64` はどちらにも入らない。`to_string_radix(10)` を経由して `i128::from_str` する形に変えた
  （`to_f64` は丸めるので使えない）。`i64` に入るうちは `to_i64` のままで、10 進文字列を作るのは本当に広いときだけ。
* **`p(x rescue :y)` が本家のパーサで通らない**（`syntax error, unexpected 'rescue' modifier`）。
  テストの Ruby を `begin`/`rescue` に書き直した。
* serde_json のパースエラーの文言（`EOF while parsing a list` だと思っていたら `a value`）をテストに
  べた書きしていて落ちた。版に依存する文字列なので、クラスと `line 1 column 3` の部分だけを見るようにした。
* 非 UTF-8 の String を `serde_json::Value` として読むと `invalid type: byte array` で落ちる。
  これは正しい振る舞い（JSON にバイト列は無い）なので、期待値をそちらに合わせ、バイトを欲しがる型は
  受け取れることを別に確かめた。

## `JSON.generate` を `from_value` 経由にしなかった

計画書は「`serde_json` の `Value` を経由するのが最短」と書いていて、`JSON.parse` はそのとおり
（`serde_json::Value` → `to_value`）。逆向きは**やめた**。`from_value::<serde_json::Value>` にすると、

* Hash の鍵は `String` でないと通らない。CRuby は `{1 => 2}` を `{"1":2}` にする（鍵は `to_s`）。
  これを通すために `deserialize_string` で Integer を `to_s` するようにすると、
  普通の struct の `String` フィールドに Integer が黙って入るようになってしまう。
* JSON にならないクラスのオブジェクトは CRuby では `to_s` になる（`(1..3).to_json` は `"1..3"`）。
  serde のデータモデルには「`to_s` を呼べ」が無い。

ので、`json.rs` に `ruby_to_json` を書き下ろした。深さ 100 で `JSON::GeneratorError`（自分を含む Array で
ホストのスタックを落とさないため。CRuby の `max_nesting` と同じ数）。

## 未解決: `cargo publish --dry-run` が verify で落ちる

`cargo publish --dry-run -p sabiruby-serde` は packaging までは通る（10 ファイル、14.2KiB）が、
verify のビルドで落ちる。crates.io に上がっている `sabiruby 0.4.0` には `src/convert.rs` も
`src/host_store.rs` も無い（`~/.cargo/registry/src/index.crates.io-*/sabiruby-0.4.0/src/` を見た）。
つまり公開済みの 0.4.0 は段階 4（`ccc60de`）より前のもので、版が上がらないまま作業ツリーだけ進んでいる。
`sabiruby-serde` は `sabiruby` を次に公開してからでないと上げられない。`--no-verify` を付けると通る。
版を上げるのは本体の判断なので、依存は `version = "0.4"` のままにしてある。
